# XDUCraft Documentation Repository

This repository contains the content for the XDUCraft documentation site. It is built with [Astro](https://astro.build/) and [Starlight](https://starlight.astro.build/), and its pages are primarily written in Markdown (`.md`) and MDX (`.mdx`).

The content is intended for XDUCraft players, server maintainers, and anyone interested in the related technical topics. It includes joining guides, modpack instructions, server setup tutorials, plugin/mod introductions, and other technical documentation. The site is only the presentation layer; the main goal is to keep the documentation accurate, clear, and reproducible.

## How to Contribute

You can help improve the documentation by:

- Writing a new guide or filling gaps in an existing guide;
- Correcting inaccurate steps, commands, links, images, or configuration details;
- Proofreading spelling, punctuation, wording, and heading structure;
- Updating content when the game, modpack, plugin, or server configuration changes;
- Reporting instructions that cannot be reproduced, are unclear, or do not match the actual situation.

If you are unsure how to make a change, open an issue first, or describe the problem in a Pull Request and ask the maintainers for help. Confirm information about server rules, addresses, accounts, security, or personal data with a maintainer before adding it to public documentation.

## Where Content Lives

```text
src/
├── assets/                 # Images and other assets
├── content/
│   └── docs/               # All documentation pages
│       ├── general/        # Overview content
│       ├── join-server/    # Getting-started guides
│       ├── server-setup/   # Java server setup guides
│       ├── index.mdx       # Documentation home page
│       └── *.md / *.mdx    # Standalone documents
└── content.config.ts       # Starlight content configuration
```

In most cases, contributors only need to modify `src/content/docs/` and the corresponding files in `src/assets/`. The site layout, sidebar, and theme configuration are in `astro.config.mjs`; explain the reason in the Pull Request or ask a maintainer to handle changes to those files.

## Adding a New Document

1. Define the intended readers, goal, and scope first. Avoid mixing unrelated topics in one article.
2. Create a `.md` or `.mdx` file in the appropriate location under `src/content/docs/`.
   - Use `.md` for regular text, code, and image-based instructions;
   - Use `.mdx` when you need Starlight components or a small amount of JSX/HTML.
3. Add frontmatter at the beginning of the file:

```yaml
---
title: Document title
description: A one-sentence summary of the document
---
```

4. Organize the content as “Prerequisites → Steps → Expected result → Common issues” when appropriate; adapt the structure to the topic instead of forcing every section.
5. Documents placed in an existing autogenerated section, such as `join-server/` or `server-setup/`, will normally appear there automatically. Standalone documents or new directories may also need an entry in the `sidebar` configuration in `astro.config.mjs`; mention this in your Pull Request.

File names affect page URLs. Do not rename or move published documents casually; when a change is necessary, also check internal links, image paths, and sidebar configuration.

## Editing or Proofreading Existing Documents

- Make focused changes where possible, preserving correct frontmatter, page URLs, and existing images;
- Include the applicable version for information that changes frequently, such as versions, download links, server addresses, and launcher interfaces;
- Format commands, file names, configuration keys, button names, and user input as inline code, for example `npm run build`;
- Make the steps reproducible. Clearly state any platform, version, or launcher-specific conditions;
- Screenshots should be clear and necessary, and should preferably not expose passwords, tokens, real email addresses, IP allowlists, or other private information;
- Use meaningful wording for image alternative text instead of generic text such as “image” or “as shown”.

## Images and Assets

Store documentation images under `src/assets/`. We recommend creating a subdirectory for each topic and using descriptive file names. For example:

```text
src/assets/my-guide/install-step-01.png
```

Reference images in Markdown with a path relative to the current document:

```markdown
![Installation interface example](../../assets/my-guide/install-step-01.png)
```

If the document is nested more deeply, adjust the number of `../` segments according to its location. Existing pages in the same directory provide useful examples. Before submitting, verify the exact casing, file name, and relative path.

## Local Preview and Astro Reference

For `.md` documents that use only standard Markdown syntax, you normally do not need to install Node.js, npm, or start the Astro site. After saving the file, use any Markdown-capable viewer—such as Obsidian or VS Code with a Markdown preview extension—to check headings, lists, code blocks, links, and images.

If the document uses MDX, Starlight components, site-specific styles, or renders differently from a regular Markdown preview, consider starting the Astro site locally. This project requires Node.js and npm; after cloning the repository, run the following commands from its root:

```bash
npm ci
npm run dev
```

Open the local URL shown in the terminal, usually `http://localhost:4321`, and check the page content, titles, navigation, links, and images.

Only run a production build when you need additional confirmation or have changed site configuration, components, or other site-level code:

```bash
npm run build
```

`dist/`, `.astro/`, and `node_modules/` are generated or dependency directories and, under the current `.gitignore` settings, will not be committed; please do not remove those ignore rules.

For the site structure, Starlight reads `.md` and `.mdx` files from `src/content/docs/`; images and other imported assets belong in `src/assets/`, while static files can be placed in `public/`. For more information about components, frontmatter, and theming, see the [Starlight documentation](https://starlight.astro.build/) and [Astro documentation](https://docs.astro.build/).

## Recommended Workflow

1. Create a branch from the latest `main`. Branch names can use `docs/<topic>` or `fix/<topic>`, such as `docs/server-backup`.
2. Write the new document, or update the relevant page and images.
3. Use a Markdown viewer for a basic preview; if you use MDX, Starlight features, or notice rendering differences, start the local site as described above.
4. Commit the changes and open a Pull Request describing what changed, why it changed, and whether maintainers should pay special attention to version or server information.
5. Address review feedback. Before merging, make sure all new files, images, and links are included in the change.

## Pre-submission Checklist

- [ ] The title, description, and body accurately represent the document;
- [ ] The steps, commands, and version information have been checked against reality;
- [ ] All images render correctly, with meaningful alternative text and valid relative paths;
- [ ] Internal links, external links, and sidebar entries work;
- [ ] Whether passwords, tokens, personal data, or server information that should not be disclosed are submitted;
- [ ] The document has been checked with a Markdown viewer; special features have been previewed in the local site when needed;
- [ ] The Pull Request clearly explains what changed and why.

Thank you to everyone who helps make the XDUCraft documentation more accurate and easier to use.
